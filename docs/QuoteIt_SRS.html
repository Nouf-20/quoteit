1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines the functional and non-functional requirements of QuoteIt, a web platform for publishing and managing quotes. It is the reference document for the final version of the project and describes what the system does, how users interact with it, and the constraints it must satisfy.

1.2 Scope

QuoteIt allows visitors to browse all published quotes without an account. Registered users can create an account, log in, publish quotes, edit or delete their own quotes, and log out. The final version adds one new feature: like/unlike with persistent like counts. All data is stored in a relational database; no quote data is hardcoded in the views.

The system deliberately excludes features that are not required by the project brief, such as private messaging, quote categories, password reset, and moderation tools.

1.3 Definitions

TermDefinition
GuestAn unauthenticated visitor who can browse quotes.
Registered UserAn authenticated account holder who can publish and manage their own quotes.
QuoteA short text of 3–155 characters published by a registered user.
OwnerThe user who created a quote; only the owner may edit or delete it.
LikeA persistent association between one user and one quote. A user may like a quote at most once.
Like countThe number of distinct users who currently like a quote.
CSRFCross-Site Request Forgery protection token included in every state-changing form.

2. Overall Description

2.1 Product Perspective

QuoteIt is a standalone Laravel web application following the MVC pattern. Blade templates provide the presentation layer, controllers handle requests and validation, Eloquent models map the domain entities, and migrations/seeders create and populate the database. The public quote feed is the entry point of the application.

2.2 User Classes

User classCapabilities
Guest Browse all quotes (text, author name, publication date, like count). Open sign-up and login pages.
Registered User Everything a guest can do, plus publish quotes, edit/delete own quotes, like/unlike any quote, and log out.

2.3 Operating Environment

StylingTailwind CSS compiled with Vite
ClientAny modern web browser; responsive on mobile and desktop

2.4 Constraints and Assumptions

  • All views must use Blade template inheritance (@extends, @yield) and Blade components.
  • Every form field must display a short hint describing the allowed input.
  • Passwords must be stored hashed; plain-text passwords must never be persisted.
  • Only the owner of a quote may edit or delete it.
  • The quotes page must load within 3 seconds.
  • Users are assumed to have a valid email address and a modern browser.

3. System Features

FR-01 — View quotes. The system shall display every published quote to every visitor, including guests, showing the quote text, the author's name, and the publication date.

3.1 View Quotes

Actors: Guest, Registered User. Preconditions: none.

Main flow: The user opens the home page → the system retrieves all quotes with their authors and like counts from the database → the system renders the quotes list ordered from newest to oldest → each card shows the quote text, author name, date, and like count.

Postconditions: The quotes list is visible; guests see login/sign-up links; registered users additionally see the share form and like buttons.

Acceptance criteria: A guest visiting / sees the quotes with author and date; the data comes from the database, not from hardcoded view data.

FR-02 — Create account. The system shall allow a visitor to register with a name of 2–50 characters, a valid unique email address, and a password of at least 8 characters.

3.2 Create Account

Actor: Guest. Preconditions: the visitor is not authenticated.

Main flow: The visitor opens the sign-up page → enters full name, email, password, and password confirmation → submits the form → the system validates all fields → the password is hashed → the user record is created → the user is logged in and redirected to the home page.

Alternative flows:

  • Name shorter than 2 or longer than 50 characters → validation error displayed next to the field.
  • Email is invalid or already registered → validation error displayed next to the field.
  • Password shorter than 8 characters or confirmation does not match → validation error displayed next to the field.

Postconditions: A new user exists with a hashed password, and an authenticated session is active.

Acceptance criteria: Valid data creates an account and logs the user in; invalid data is rejected with a visible message and the form is not submitted to the database.

FR-03 — Log in. The system shall authenticate a registered user using their email address and password.

3.3 Log In

Actor: Guest (registered user). Preconditions: an account exists.

Main flow: The user opens the login page → enters email and password → the system verifies the credentials against the stored hash → the session is regenerated → the user is redirected to the home page.

Alternative flow: Credentials do not match → a general error is shown and the email is preserved in the form.

Acceptance criteria: Correct credentials authenticate the user; incorrect credentials do not create a session.

FR-04 — Log out. The system shall allow an authenticated user to end their session.

3.4 Log Out

Actor: Registered User. Preconditions: the user is authenticated.

Main flow: The user presses “Log out” in the header → the system invalidates the session and regenerates the CSRF token → the user is redirected to the home page as a guest.

Acceptance criteria: After logout, protected actions are no longer available and the header shows login/sign-up links.

FR-05 — Share a quote. The system shall allow an authenticated user to publish a quote of 3–155 characters.

3.5 Share a Quote

Actor: Registered User. Preconditions: the user is authenticated.

Main flow: The user writes the quote in the share form → submits → the system validates the length → the quote is stored with the authenticated user's ID and the current timestamp → the page reloads and the new quote appears at the top of the list.

Alternative flows: Fewer than 3 or more than 155 characters → a validation error is displayed and nothing is stored.

Postconditions: The quote is persisted in the database and visible to all visitors.

FR-06 — Edit own quote. The system shall allow a user to edit only the quotes they created.

3.6 Edit Own Quote

Actor: Registered User (owner). Preconditions: the user is authenticated and owns the quote.

Main flow: The owner selects “Edit” on their quote → the edit form opens with the current text → the owner changes the text and submits → the system verifies ownership and validates the length → the quote is updated.

Alternative flows: The user is not the owner → the system responds with HTTP 403 and does not reveal the edit form. Invalid length → validation error.

Acceptance criteria: Owners can update their quotes; other users cannot access the edit route or persist changes.

FR-07 — Delete own quote. The system shall allow a user to delete only the quotes they created.

3.7 Delete Own Quote

Actor: Registered User (owner). Preconditions: the user is authenticated and owns the quote.

Main flow: The owner selects “Delete” and confirms → the system verifies ownership → the quote and its likes are deleted → the list refreshes without the quote.

Alternative flow: A non-owner attempts deletion → HTTP 403; the quote remains unchanged.

FR-08 — Like / unlike a quote (new feature). The system shall allow an authenticated user to like or unlike any quote and shall display the stored like count on every quote.

3.8 Like / Unlike a Quote (New Feature)

Actor: Registered User. Preconditions: the user is authenticated and the quote exists.

Main flow: The user presses the heart button on a quote → the system toggles the like for that user → the association is stored in quote_likes → the page reloads and the heart state and count update.

Alternative flow: A guest sees the like count but not an interactive like button; guests are invited to log in.

Business rules:

  • A user can like a given quote at most once; pressing again removes the like.
  • Like counts are computed from the database and are visible to guests and registered users.
  • Deleting a quote also deletes its likes (cascade).

Acceptance criteria: Liking increments the count, unliking decrements it, the count persists after a reload, and the toggle only works for authenticated users.

5. Non-Functional Requirements

CategoryRequirementImplementation
Security — password storage Passwords must be hashed, never stored as plain text. Laravel hashed cast on User::$password; bcrypt hashing.
Security — authorization Only the owner may edit or delete a quote; others may only read it. Authenticated routes plus server-side ownership check returning HTTP 403.
Security — request forgery State-changing forms must be protected. CSRF tokens on every POST/PUT/DELETE form; session regenerated on login and logout.
Usability — hints Every form field must show a short hint about allowed input. Reusable <x-form-hint> component on every field.
Usability — first quote A new user must be able to publish a first quote in under one minute. Share form is at the top of the home page after login; a single field and one submit button.
Performance The quotes page must load within 3 seconds. Single indexed query with eager loading and aggregate like count; compiled assets; measured locally at well under 1 second.
Reliability / integrity Data must remain consistent. Foreign keys with cascade delete; unique constraint on (quote_id, user_id).
Maintainability The code must follow the framework conventions. MVC separation, migrations, seeders, reusable Blade components, automated tests.
Portability The application should run on a standard PHP/Laravel environment. Standard Laravel structure; environment-driven database configuration.

6.2 Relationships

  • A user has many quotes; each quote belongs to exactly one user.
  • A user has many likes; each like belongs to one user.
  • A quote has many likes; each like belongs to one quote.
  • Users and quotes form a many-to-many relationship through quote_likes.

The complete entity relationship diagram is provided separately as QuoteIt_ERD.pdf.

8. Changes from the Original SRS

  • New feature — Likes: added the quote_likes table, toggle action, and like counts. This satisfies the mandatory “at least one new feature” requirement.
  • Database integration: quotes, users, and likes are persisted in SQLite instead of static view data.
  • Authentication: completed sign-up, login, logout, validation, and session handling.
  • Authorization: added owner-only edit/delete with server-side enforcement.
  • User interface: restored the quote feed with Blade components, responsive cards, hints, error messages, and success alerts.
  • Seed data: added a demo account and eight cybersecurity quotes with varied authors and dates.
  • Testing: enabled database refresh for feature tests and verified the full flow over HTTP.

10.2 Run the Project

  1. Install PHP 8.3+ and Composer.
  2. Run composer install.
  3. Copy .env.example to .env and run php artisan key:generate.
  4. Ensure database/database.sqlite exists, then run php artisan migrate --seed.
  5. Run npm install && npm run build (or npm run dev).
  6. Run php artisan serve and open http://127.0.0.1:8000.
